### UI golden rules (checked throughout)

- **Panels never cover the workspace** — measured, not eyeballed: the tool dock's left edge and the viewer's right edge meet at x=1018 with zero overlap, on every panel (Organize, Bates, Stamps, OCR, Redaction, Centurion). The find bar likewise pushes the pages down (findBottom 293 = viewerTop 293).
- **Movement is shown** — OCR's counter was captured ticking through `PAGE 0/1/3/5/6 OF 6` with named phases; redaction streams `Rasterizing page N/4 → Rebuilding page N/4 → Verifying`; combine, split, reorder, Bates and watermark all stream per-page progress. *One weak spot:* the 500-page Bates run emits all 500 events in ~39 ms, so the on-screen counter never renders an intermediate value — the user sees "Starting" then done. Harmless at 1.7 s, but it means the Bates progress bar is decorative rather than informative.
- **Refresh after mutation** — page grid, page count, footer, and thumbnails all updated without any manual refresh after every op.
- **Plain English** — every receipt and error read like a sentence an attorney would write ("Removed 1 page. 8 left.", "Pages rearranged.", "The redaction was NOT applied…"). No jargon, no stack traces, no emojis, anywhere.
- **Dirty markers / footer state** — correct in every observed transition.

## 2. Findings

### F-1 · Medium · No path-taking Save As — scripted or repeatable workflows are impossible
`file.saveAs(docId, suggestedName?)` always opens the OS save dialog
(`electron/ipc/file.ts:53`), and `window.librarius` is deep-frozen by
`contextBridge`, so nothing outside the app can supply a path. Consequences:
(a) every output file in this report had to be extracted through `file.read()`
and written WSL-side, because the app cannot be asked to save to a path;
(b) an attorney cannot batch anything — 30 exhibits means 30 dialog trips;
(c) any future automation of Librarius is blocked at this seam.
*Repro:* call `window.librarius.file.saveAs(docId, 'C:\\path\\out.pdf')` — the
second argument is only a suggested **name**, and a dialog still opens.
*Suggested fix:* accept an optional absolute path that bypasses the dialog.

### F-2 · Medium · The recent-files list has no UI
`file:recent` / `file:recentClear` are implemented and persist correctly
(10 entries survived an app restart in this run), and `RecentFile` is in the
shared types — but nothing in `src/` ever calls them. `grep -rn "recent" src/`
returns zero hits. The empty state offers only "Drop a PDF here or press
Ctrl+O". PRD F-1 lists "recent list" as a shipped way to open a document.
*Repro:* start the app, look at the empty state; then run
`await window.librarius.file.recent()` in the console and see the data that is
being kept but never shown.

### F-3 · Medium · Bookmarks are read-only in the UI
`ops:bookmarksSet` works (verified end-to-end: write → save → reopen → rename →
reopen), but `src/components/thumbnails/bookmark-tree.tsx` renders a read-only
tree and no component calls `bookmarksSet`. An attorney can see and click
bookmarks but cannot create, rename, delete, or re-target one — which is most of
what bookmarking a 500-page exhibit set is for.

### F-4 · **High** · Closing a tab with unsaved changes discards the work silently
`closeDocument()` (`src/app/document-actions.ts:113`) calls `file.close()` and
drops the session with no confirmation. *Repro, verified live:* open a PDF,
apply a watermark (tab shows the unsaved dot, footer reads UNSAVED CHANGES),
click the tab's ✕. The tab disappears immediately — no dialog, no toast, no
undo, and the edit is gone. On this build that is one mis-click between an
attorney and a re-done 500-page Bates run. Everything else in this app is
scrupulous about not losing data, which makes this the one place the discipline
breaks.
*Suggested fix:* the same `window.confirm` pattern already used for removing a
signature, or an offer to Save first.

### F-5 · Medium · The print dialog blocks the whole app, and an abnormal close wedges it
`webContents.print({ silent: false })` opens a native modal (`#32770`,
title `legion-librarius`). While it is up the renderer answers nothing — a
normal consequence of a native modal, but it means a print dialog left open
behind another window looks exactly like a hang. In this run, closing that
dialog with a posted `WM_CLOSE` (rather than clicking Cancel) left the app
permanently unresponsive and it had to be killed and relaunched. **Caveat: I
induced this; a user pressing Cancel was not tested and probably recovers
normally.** Worth a look because the failure mode is a silent, total wedge.

### F-6 · Low · Watermark text is not searchable
See check 9. Rotated watermark glyphs extract as `D`, `R`, `A`, `FT` rather than
`DRAFT`, so Ctrl+F for the watermark finds nothing. Visual output is correct.

### F-7 · Low · Redaction defaults to a non-searchable output
"Keep the redacted pages searchable" is **off** by default
(`redaction-store.ts:162`). With the default, the redacted document comes back
as a pure 300 DPI raster: every page extracts to an empty string, so a produced
set is unsearchable unless the attorney notices the checkbox. Turning it on
works perfectly (verified). Consider defaulting it on, or saying in the receipt
that the output is now a picture.

### F-8 · Low · Combine cannot use documents already open in tabs
`CombineView` seeds the list with the active document and adds everything else
through the OS picker (`combine-view.tsx:52`). Three PDFs already open in three
tabs still have to be re-found on disk.

### F-9 · Low (cosmetic) · The status footer's notice is sticky across documents
A receipt line such as "SIGNED PAGE 1. THE SIGNATURE IS PART OF THE PAGE NOW."
stayed in the footer while a *different* document was open several operations
later. `setNotice` is never cleared on tab switch or new op.

### Observed once, not reproduced
A text-box placement click did not register on the first attempt shortly after
a page jump (the "Add this text to page N" button never appeared); a repeat
click worked, and a targeted repro attempt was inconclusive. Possibly the
documented `clientToPdf` null window between page renders. Flagged rather than
claimed.

### How the app was driven

File dialogs cannot be driven over CDP, and `window.librarius` is deep-frozen,
so it could not be stubbed. Documents were therefore opened the way the attorney
does — **real drag-and-drop**: a hidden `<input type=file>` was fed real OS paths
via `DOM.setFileInputFiles`, and the resulting `File` objects (which
`webUtils.getPathForFile` can resolve) were dispatched as a `drop` on the
viewer. Every feature was exercised by clicking the app's own controls; the
bridge was called directly only where no UI exists (combine's file list,
`bookmarksSet`) or to extract output bytes for verification. Document ids were
read from the tab list's React fiber keys.
